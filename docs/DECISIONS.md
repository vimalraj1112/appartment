# SuperLink Community — Architectural Decisions

Format: `[phase] Decision — rationale (one line each)`

## Phase 1 (pre-coding)
- Monorepo uses npm workspaces (not pnpm/turbo) — zero extra tooling on Windows, sufficient for 3 packages.
- Role is a single enum column on `users`; RBAC source of truth is `packages/shared/src/rbac.ts` (code), not DB tables — matrix generates both route guards and tests; avoids drift.
- Tenant isolation via AsyncLocalStorage + Prisma `$extends` query hook at repository layer — controllers never receive an unscoped client.
- Cross-tenant reads only via `withPlatformClient()`, always writing an AuditLog entry.
- IDs from Community B return 404 (not 403) to prevent existence leaks.
- Access token 15 min in memory; refresh token rotation in HTTP-only cookie with reuse detection + server-side Session records.
- Mock providers (email, payment, push, whatsapp, LLM, storage-local) live in `src/mocks/` and are never imported by production service factories (factory picks by env).
- API response envelope `{ success, data, error:{code,message}, meta }` — all errors friendly, never raw.
- Single API process hosts HTTP + Socket.IO + BullMQ in v1; worker entrypoint separated for future scale-out.
- Generated bills guarded by UNIQUE(flatId, period) — idempotency enforced by DB, not app logic.
- Amenity double-booking prevented by DB unique constraint on (amenityId, date, slotStart) for BOOKED status inside a transaction.
- QR passes are signed HMAC tokens carrying passId + communityId + expiry; verification is server-side only.
- AI assistant: LLM never touches DB; fixed tool set re-verifies session identity/role/ownership; all tool calls logged.
- Design tokens implemented once as a Tailwind preset + `animations/variants.ts` shared by every phase.

## Phase 2
- `communityId` is denormalized (non-null, indexed) onto Floor, Flat, FlatOccupant, FamilyMember, ResidentDocument and Invitation even though it is derivable via parent relations — gives uniform, single-column tenant scoping and matches the `$extends` hook's `communityId` injection (deviation from the outline, recorded here).
- Owner/tenant are modeled through `FlatOccupant.relation` (OWNER|TENANT) with `isPrimary` + `movedInAt`/`movedOutAt` history; `Flat` has no `ownerUserId`/`tenantUserId` columns — one occupancy table serves owners, tenants and future co-occupants.
- Services keep Prisma queries inline (no separate repository layer) to match Phase 1; the tenant `$extends` client remains the enforcement boundary.
- `ResidentDocument` model + `TENANT_MODELS` entry added in Phase 2 but its API/UI is deferred until the StorageAdapter lands (Phase 14) — no file uploads yet.
- Authenticated tenant-model `create` calls pass a `communityId: ""` placeholder that the `$extends` hook overwrites with the real tenant id at runtime (Prisma's generated types require the column); bypass/system writes (invitation accept) pass the real `communityId` explicitly.
- Bulk flat creation is idempotent via `createMany({ skipDuplicates })` on the UNIQUE(communityId, code) constraint and reports created/skipped counts.
- Public invitation accept resolves the token through `runAsSystem()` (token is the credential) and activates INVITED users in place; invitations are single-use (`acceptedAt`) and drive `CommunitySetting.onboardingStep` only as a soft checklist.

## Phase 3
- Phase 3 scope is resident dashboard + notifications + realtime + motion baseline. The "flat bill/payment ledger" item is deferred to Phase 6 (Billing) because bills/payments do not exist until then — recorded as an explicit assumption.
- `Notification` (communityId, userId, type, title, body, data Json, readAt) is a tenant model added to `TENANT_MODELS`; delivery is realtime over Socket.IO plus REST for history/read-state.
- Notifications are created through `createNotification()`, which resolves the recipient's `communityId` inside `runAsSystem()` and creates with the explicit id, so it works identically in request and system contexts; in a tenant context an admin can only notify users in their own community (cross-community send → 403).
- Socket.IO authenticates the handshake with the same short-lived access token (`verifyAccessToken`); authenticated sockets join `user:{userId}` and `community:{communityId}` rooms; `notification:new` is emitted to the user room. `initSocket`/`closeSocket` are explicit so tests can bind an ephemeral port.
- New RBAC capabilities `DASHBOARD_VIEW` + `NOTIFICATION_VIEW` granted to all roles, `NOTIFICATION_SEND` to SUPER_ADMIN/COMMUNITY_ADMIN.
- Web realtime uses a socket.io-client singleton bound to the access token, connected from `AuthProvider` on auth / disconnected on logout; dev proxies `/socket.io` (ws) to the API alongside `/api`.
- Dashboard and notifications are self-scoped endpoints (`/dashboard`, `/notifications`) reading the caller's own userId from the token — no extra permission checks beyond `*_VIEW`.

## Phase 4
- New tenant models: `Visitor`, `VisitorPass`, `VisitorEntry`, `Delivery`, `DeliveryEntry`, `WatchlistEntry` (all added to `TENANT_MODELS`). `VisitorPhoto` is deferred to Phase 14 with the StorageAdapter (no file uploads yet).
- A pass holds a short human `code` (unique per community, used for manual entry and in-app QR) and an opaque `qrToken` stored only as `qrTokenHash` (sha256); the raw token is returned once at creation as a shareable public link (`/pass/:token`). In-app QR encodes the `code`, verified by authenticated guards.
- `VisitorPassStatus` was extended beyond the outline with `PENDING` to model guard walk-in requests that need resident approval; resident/admin-created passes start `ACTIVE`, walk-ins start `PENDING` and flip to `ACTIVE`/`CANCELLED` via the decision endpoint.
- Resident scoping for visitors is by active flat occupancy (`FlatOccupant.movedOutAt = null`); managers (CA/SECURITY/SA) see the whole community. Cross-community reads return 404 via the tenant extension.
- Scanning does not auto-record entry: `POST /visitors/verify` is read-only (also flags watchlist matches by name/phone); the guard then records `IN`/`OUT` via `POST /visitors/entries`, which increments `usedCount` and marks a single-use pass `USED`.
- Deliveries and watchlist are manager-only mutations (`DELIVERY_MANAGE` / `WATCHLIST_MANAGE` = CA+SECURITY); residents read their own deliveries/passes/entries via `VISITOR_VIEW`. Gate operations (verify/entries/walk-in/flats lookup) require `GATE_OPERATIONS` (CA+SECURITY), so residents cannot scan and guards cannot create passes.
- Walk-in creation and delivery status changes emit in-app notifications to the flat's active occupants (reuses Phase 3 `createNotification`).
- Web: resident `/app/visitors` (+ `/new`), guard `/guard/scan` + `/guard/visitors`, admin `/admin/visitors` + `/admin/security`, and the public `/pass/:token` page.

## Phase 5
- New tenant models: `ComplaintCategory`, `Complaint`, `ComplaintComment`, `StaffProfile`, `StaffAssignment`, `StaffEntry`, `DomesticStaff` (all added to `TENANT_MODELS`). `ComplaintAttachment` is deferred to Phase 14 with the StorageAdapter (no file uploads yet).
- Complaint lifecycle uses enums `ComplaintPriority` (LOW|MEDIUM|HIGH|URGENT) and `ComplaintStatus` (OPEN|ASSIGNED|IN_PROGRESS|RESOLVED|CLOSED); `resolvedAt`/`closedAt` are stamped on transition and a single 1–5 `rating` is captured post-resolution.
- Complaint scoping is role-based in the service layer: residents see complaints they raised or that belong to a flat they actively occupy; STAFF sees only `assignedToId = self`; CA/SA see the whole community. Cross-community reads/writes return 404 via the tenant extension.
- `isInternal` comments are only honored for CA/SA/STAFF; a resident's internal flag is ignored and residents never receive internal comments in `GET /complaints/:id`. All visible comments are notified to the counterpart (resident comment → admins; staff/admin comment → raiser).
- Assignment is admin-only (`COMPLAINT_MANAGE`) and writes a `StaffAssignment` history row inside the same transaction as the complaint update, plus a notification to the assigned staff member. Status changes notify the flat's active occupants.
- New RBAC capabilities: `COMPLAINT_RAISE` (CA, RESIDENT), `COMPLAINT_MANAGE` (CA), `COMPLAINT_WORK` (CA, STAFF), `COMPLAINT_VIEW` (CA, RESIDENT, STAFF), `COMPLAINT_CATEGORY_MANAGE` (CA), `STAFF_MANAGE` (CA), `STAFF_ENTRY` (CA, SECURITY), `DOMESTIC_STAFF_MANAGE` (CA, RESIDENT).
- `StaffProfile` is one-to-one with a STAFF user (unique `userId`); a STAFF user without a profile cannot be assigned work until the admin registers one. `GET /staff/users` (STAFF_MANAGE) lists active STAFF users so the admin UI can pick a user when creating a profile.
- Domestic staff are registered per flat and scoped like visitors (resident = own active flats, CA/SECURITY = all); `StaffEntry` IN/OUT reuses `VISITOR_ENTRY_DIRECTIONS`.
- Web: resident `/app/complaints` (+ `/new`, `/:id`), staff `/app/tasks`, admin `/admin/complaints` (+ `/:id`) and `/admin/staff`; the shared complaint detail page adapts actions to the viewer's role.

## Phase 6
- New tenant models: `MaintenanceConfig`, `MaintenanceBill`, `MaintenanceBillItem`, `Payment`, `PaymentReceipt`, `ExpenseCategory`, `Expense` (all added to `TENANT_MODELS`). Enums `BillStatus` (PENDING|PARTIAL|PAID|OVERDUE), `PaymentStatus` (PENDING|PROCESSING|SUCCESS|FAILED|REFUNDED), `PaymentProvider` (MOCK|RAZORPAY|CASH|BANK_TRANSFER|UPI). `PaymentReceipt.fileKey` column exists but is deferred to Phase 14 with the StorageAdapter (PDF generation not in scope).
- This phase absorbs the "flat bill/payment ledger" item deferred from Phase 3; money is stored as whole-rupee `Int` (`*Inr`) — no floats, no currency minor-unit handling in v1.
- One `MaintenanceConfig` per `(communityId, flatType)`; a bill is generated by summing the non-zero line items (base/water/parking) for the flat's type. Due date defaults to the 10th of the month AFTER the period.
- Bill generation is idempotent at the DB level via `UNIQUE(flatId, period)`; re-running skips existing bills and reports created/skipped. Occupants are notified on generation.
- `POST /billing/bills/overdue` is an explicit sweep (not a cron): it stamps `OVERDUE` and appends a single "Late fee" item (guarded so it is added at most once) using the flat type's `lateFeeInr`.
- Payments go through a `PaymentProviderAdapter`: `MOCK` (default, instant SUCCESS) and `RAZORPAY` (creates an order → PROCESSING; FAILED if keys missing), selected by `PAYMENT_PROVIDER` env. A receipt is issued only on SUCCESS. Manual capture (CASH/BANK_TRANSFER/UPI) records an immediate SUCCESS via `POST /payments/manual`.
- Idempotency: `Payment.idempotencyKey` (client-generated UUID) has `UNIQUE(communityId, idempotencyKey)`; replaying the same key returns the original payment. Overpay and already-PAID bills are rejected.
- Global unique constraints on tenant models break an accumulating test DB, and nested `create` inside a parent write is NOT auto-scoped by the tenant hook — so `Payment.idempotencyKey` and `PaymentReceipt.receiptNo` use `@@unique([communityId, field])`, and services create the bill first then its items with a separate top-level `createMany` (never `communityId: ""` inside a nested create).
- RBAC reuses `BILLING_CONFIGURE` (CA), `FINANCE_VIEW` (CA), `BILL_VIEW_OWN` (RESIDENT), `BILL_PAY` (RESIDENT); bill read routes use the new `requireAnyPermission("BILL_VIEW_OWN","FINANCE_VIEW")`. SECURITY is blocked from every `/billing`, `/payments`, `/expenses` route.
- Web: resident `/app/bills` (+ `/app/bills/:id` pay/receipts), admin `/admin/billing` (charges, generate, collect, summary) and `/admin/expenses`; billing badge/currency helpers live in `features/billing/components.tsx`.

## Phase 7
- New tenant models: `Amenity`, `AmenityBooking`, `Vehicle`, `ParkingSlot`, `ParkingAssignment`, `ParkingVisitor` (all added to `TENANT_MODELS`). Enums `BookingStatus` (BOOKED|CANCELLED|WAITLISTED), `VehicleType` (CAR|BIKE|EV|BICYCLE), `ParkingSlotStatus` (AVAILABLE|OCCUPIED|RESERVED|MAINTENANCE).
- Amenities are community inventory (`@@unique([communityId, name])`) with `slotMinutes`, `capacity`, `openTime`/`closeTime` (local `HH:mm` strings), `feeInr`, `rules`, `isActive`. Bookings are slot-based on a `@db.Date` column; the service validates the slot is aligned to the amenity's open/close window and slot length before writing.
- Waitlist is folded into `AmenityBooking` (`status = WAITLISTED` + `waitlistPosition`) rather than a separate model. Creating a booking when the slot is at capacity enqueues it; cancelling a `BOOKED` booking auto-promotes the lowest-position waitlisted booking for that amenity+date+slot and notifies the flat's occupants.
- There is deliberately no DB unique on bookings: duplicate-per-flat and capacity checks are enforced in the service (a flat cannot hold two active bookings for the same amenity+date+slot). This keeps waitlist/capacity logic in one place.
- Resident booking scope is by active flat occupancy; admins book on behalf of a flat (`flatId` required). Cancelling is scoped so a resident can only cancel a booking for their own flat (cross-tenant/cross-flat → 404).
- Vehicles use `@@unique([communityId, regNumber])` (normalized uppercase, spaces stripped) so duplicate registration returns 409 rather than leaking a DB error. Residents see only their own/flat vehicles; `VEHICLE_SEARCH` (SECURITY) sees the whole community. `isGuest` marks pre-authorised visitor vehicles.
- Parking slots use `@@unique([communityId, code])`; slots are community inventory readable by residents (`PARKING_VIEW`). Assignment requires `PARKING_MANAGE` (CA), blocks double-assignment (one active assignment per slot where `endsAt = null`), flips the slot to `OCCUPIED`, and releasing flips it back to `AVAILABLE`. `ParkingVisitor` records visitor vehicles at the gate and does not mutate slot status.
- New RBAC capabilities: `AMENITY_VIEW` (CA+RESIDENT), `AMENITY_MANAGE` (CA), `BOOKING_CREATE`/`BOOKING_VIEW` (CA+RESIDENT), `BOOKING_MANAGE` (CA), `VEHICLE_OWN` (CA+RESIDENT), `VEHICLE_SEARCH` (CA+SECURITY), `PARKING_MANAGE` (CA), `PARKING_VIEW` (CA+SECURITY+RESIDENT), `PARKING_VISITOR_MANAGE` (CA+SECURITY). Cancelling uses `requireAnyPermission("BOOKING_MANAGE","BOOKING_CREATE")` (admins manage, residents cancel their own).
- Web: resident `/app/amenities` (slot grid + waitlist + cancel) and `/app/vehicles` (register / guest pre-auth); admin `/admin/amenities` (configure + toggle + cancel bookings) and `/admin/parking` (slots, assignments, release); guard `/guard/parking` (slot availability + visitor vehicle entry). guard `/guard/parking` (slot availability + visitor vehicle entry). Helpers live in `features/amenities/`.

## Phase 8
- New tenant models: `Announcement`, `AnnouncementAck`, `CommunityPost`, `CommunityComment`, `CommunityReaction`, `PostReport` (all added to `TENANT_MODELS`). Enums `AnnouncementType` (GENERAL|URGENT|MAINTENANCE|EVENT|EMERGENCY), `AnnouncementStatus` (DRAFT|SCHEDULED|PUBLISHED|ARCHIVED), `PostStatus` (VISIBLE|HIDDEN|REMOVED), `PostReportStatus` (OPEN|RESOLVED|DISMISSED). `Community`/`User` got explicit back-relations with distinct relation names (`AnnouncementAuthor`, `AnnouncementAckUser`, `PostAuthor`, `CommentAuthor`, `ReactionUser`, `ReportReporter`) because a user is related to the feed in several ways.
- Announcements are manager-authored (`ANNOUNCEMENT_MANAGE` = CA only) and community-wide. Visibility rule: managers see every status; everyone else sees only `PUBLISHED` with `publishAt <= now` (drafts/scheduled/future → 404, not 403, to avoid leaking existence). Notifications are fanned out to active community members via `createNotification` when an announcement becomes published, excluding the author.
- Acknowledgements are idempotent via `@@unique([announcementId, userId])` (upsert). Only managers receive the full ack roster; residents get their own `myAck` flag and the aggregate count only.
- Community feed is available to COMMUNITY_ADMIN + RESIDENT (`FEED_WRITE`); SECURITY/STAFF cannot post or read the feed. Non-moderators only ever see `VISIBLE` posts; an author can still open their own hidden/removed post (author-or-moderator visibility for single-post reads). Moderation (`FEED_MODERATE`, CA only) sets `status` (`VISIBLE|HIDDEN|REMOVED`) plus `hiddenReason`.
- Reactions are a per-user toggle: one row per `[postId, userId]` (`@@unique`); reacting with the same emoji removes it, a different emoji replaces it. Reports are deduplicated per `@@unique([postId, reporterId])` and increment `CommunityPost.reportedCount` on first report only. Reports are moderated (`listReports`/`resolveReport`, statuses OPEN|RESOLVED|DISMISSED) under `FEED_MODERATE`.
- Announcements notify via the existing notification service; to avoid nested tenant-scoping issues the service resolves recipients with a scoped `user.findMany` and calls `createNotification` per user (system context). `ANNOUNCEMENT_READ` is granted to all roles (incl. STAFF/SECURITY); `FEED_WRITE` to CA+RESIDENT; `FEED_MODERATE`/`ANNOUNCEMENT_MANAGE` to CA.
- Web: resident `/app/announcements` (filter + read + acknowledge) and `/app/community` (post/comment/react/report feed); admin `/admin/posts` (compose/publish/archive/delete + ack counts) and `/admin/community` (post moderation + report queue). STAFF nav points at `/app/announcements` (read-only; no feed access). Feature code lives in `features/community/`.
- Deferred: announcement attachment media and post images (no storage until Phase 14); `NotificationPreference` (per-user channel/type preferences) also deferred.

## Phase 9
- New tenant model: `EmergencyAlert` (added to `TENANT_MODELS`). Enums `EmergencyCategory` (MEDICAL|FIRE|SECURITY|ELECTRICAL|WATER|OTHER) and `EmergencyAlertStatus` (TRIGGERED|ACKNOWLEDGED|RESOLVED). `Community`/`Flat`/`User` got back-relations; the three responder relations use distinct names (`EmergencyTriggeredBy`/`EmergencyAcknowledgedBy`/`EmergencyResolvedBy`) with `SetNull` on the two responder FKs, and it is indexed on `(communityId, status)`. Migration `20261009153435_phase9_emergency`.
- RBAC: `EMERGENCY_VIEW` now includes RESIDENT (was SA/CA/SG); `EMERGENCY_TRIGGER` SA/CA/SG/RS; new `EMERGENCY_MANAGE` (acknowledge/resolve) limited to CA/SG. STAFF is blocked from every emergency route.
- Trigger scoping: residents must trigger for a flat they actively occupy (explicit foreign `flatId` → 403; no occupancy → validation error; omitted → their first active flat). CA/SG may raise a general alert (no flat) or target a validated flat. Responders (active CA/SG) get a `createNotification` of type `EMERGENCY`, and a Socket.IO `emergency:alert` event is emitted to the community room.
- Spam protection is server-side: (1) a user with an existing `TRIGGERED`/`ACKNOWLEDGED` alert cannot raise another (409); (2) more than 5 alerts per user in a rolling 10-minute window returns `RATE_LIMITED` (429). The web hold-to-trigger is only a UX affordance.
- Lifecycle: `TRIGGERED → ACKNOWLEDGED → RESOLVED`. Acknowledge requires status `TRIGGERED` (else 409) and sets `acknowledgedById`/`acknowledgedAt`; resolve is allowed from either active state (else 409) and sets `resolvedById`/`resolvedAt`. One shared `note` column holds the triggerer/responder note. Resident reads are scoped to their own `userId` or their flats (cross-flat/cross-community → 404).
- Web: resident `/app/emergency` (category picker + hold ~1.8s to trigger + own alert history), guard `/guard/emergency` (live active queue with ack/resolve, auto-refetch on the realtime event), admin `/admin/emergency` (filter + resolve). `onEmergency` handler added to the web socket client. Nothing deferred this phase.

## Phase 10
- No new models or migrations: reports are read-only aggregations over existing tables via `services/report.service.ts` (`groupBy`/`aggregate`/`count`). All queries run through the same tenant extension, so every number is community-scoped; direct cross-community reads are not possible.
- Route split protects the finance hard rule: community analytics live under `/reports/*` guarded by `REPORTS_VIEW` (CA only, SECURITY blocked), while the guard shift handover is mounted at `/handover` guarded by `GATE_OPERATIONS` (CA + SECURITY) so gate operators never touch a finance path. `requirePermission` also blocks STAFF/RESIDENT from both.
- Endpoints: `GET /reports/overview` (flats/occupancy, residents, visitors, complaints + avg resolution hours, current-cycle billing + overdue + collection rate, this-month expenses, active emergency), `GET /reports/trends?months=` (billed vs collected per month), `GET /reports/breakdown` (complaints by status/priority/category, expenses by category 30d, emergency by category 30d), `GET /reports/scorecard`, `GET /handover?from=&to=`.
- Billing periods reuse the UTC `YYYY-MM` key from Phase 6 so the trend lines up with generated bills; "collected" is the sum of `SUCCESS` payments whose `createdAt` falls in the month window, and the current cycle's collection rate divides collections by that period's billed total (100% when nothing was billed).
- Health scorecard: weighted 0–100 across occupancy (25), collections (25), complaint resolution (25), emergency readiness (15, penalised for active alerts), gate compliance (10, share of 30d entries checked in via pass). Grades A≥90 / B≥80 / C≥70 / D≥60 / E otherwise. These weights are a product decision, isolated in `report.service.ts`.
- Handover window defaults to the last 12 hours; the report returns visitor movements (in/out/walk-ins + list), deliveries with per-status counts, staff movements, and emergency alerts (plus a live active-alert count for the next shift). The web page offers 12h/24h/48h ranges and auto-refreshes every minute.
- Web charts are hand-rolled inline SVG (`features/reports/components.tsx`: grouped bar chart, donut, score ring, metric bars) rather than adding Recharts — the codebase is deliberately dependency-light (custom UI primitives, no component/chart library) and the existing bundle already exceeds the 500 kB warning threshold. Recorded as a deviation from the outline's Recharts mention; revisit if richer charting is needed.
- Web: admin `/admin/reports` (stat tiles + collections bar chart + complaint/emergency donuts + expense list) and `/admin/scorecard` (score ring + metric bars + breakdown); guard `/guard/handover` replaces the Phase-1 `/guard/shifts` placeholder. Nothing deferred this phase.

## Phase 11
- Data model: enum `AiMessageRole` (USER|ASSISTANT|TOOL); models `AiConversation` (owner `userId`, title — per-user, intentionally NOT tenant-scoped, matching the `Session` pattern), `AiMessage` (conversationId, role, content, optional toolName/toolArgs/toolResult/tokens), and `AiToolCall` (userId, nullable communityId, tool, ok, ms). Only `AiToolCall` carries a `communityId`, so only it is registered in `TENANT_MODELS`. Migration `20261010053407_phase11_ai`.
- Provider seam `services/llm.provider.ts`: `LlmProvider` with `plan` / `summarize` / `digest`. The deterministic `MockLlmProvider` (keyword→tool routing, joins tool summaries) is the default and backs all tests; `OpenAiLlmProvider` (function-calling over an OpenAI-compatible Chat Completions endpoint) activates only when `LLM_PROVIDER=OPENAI` and `LLM_API_KEY` is set. New env: `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL`.
- Tools-only and strictly read-only: `services/ai.tools.ts` holds the registry. Tier gating mirrors the RBAC rows — `COMMUNITY` tools require `AI_COMMUNITY` (SA/CA), `OWN` tools require `AI_OWN` (RS), and `HELP` (help content) is available to everyone. The service derives the allowed set from the caller's role and refuses any tool call outside it, so a prompt cannot escalate a resident into community statistics.
- Endpoints under `/ai`, guarded by `requireAnyPermission(AI_COMMUNITY, AI_OWN, AI_HELP)` (every role): list/create/get/delete conversations, post a message, and list the tools available to the caller. `GET /ai/digest` adds `requirePermission(AI_COMMUNITY)`. Conversations are owner-scoped in the service (`where { id, userId }`); another user's conversation id returns 404.
- A turn: persist the USER message → `provider.plan` selects tool(s) → each tool run is timed and written to `AiToolCall` (success or failure) → `provider.summarize` renders the final reply → TOOL and ASSISTANT messages are persisted → the conversation is touched and auto-titled from its first message. At most 3 tool calls per turn; tool results are JSON round-tripped before storage so Date values persist cleanly.
- Weekly digest: `getDigest` composes the Phase-10 overview into `provider.digest` for a headline summary + highlight badges, and also returns the key scoped metrics.
- Web: a single `AssistantPage` (chat + conversation list + optional digest panel) is reused at resident/staff `/app/assistant` (replaces the Phase-1 placeholder), admin `/admin/ai` (`showDigest`), and guard `/guard/assistant`. Voice input is a Web Speech API stub (mic button, disabled with a tooltip where unsupported). Nav gains an Assistant entry for CA and SECURITY.
- Deviations/assumptions: the outline's "weekly AI digest" is delivered as an on-demand admin summary rather than a scheduled cron/queue job (no worker yet); "voice input" is a client-side stub. Both to be revisited when background jobs land.



## Phase 12
- Super-admin platform console. No new models or migrations: reuses the existing `SubscriptionPlan`, `Subscription`, `AuditLog`, `Community` and `CommunitySetting` tables. Cross-tenant work relies on the platform role carrying no `communityId`, which makes the tenant extension bypass scoping (`config/prisma.ts`); rather than a separate `withPlatformClient`, SUPER_ADMIN-only routes plus explicit-`communityId` writes (community settings / subscription) provide the audited escape hatch, and every mutation writes a `PLATFORM.*` action to `AuditLog`.
- RBAC: four new caps, all SUPER_ADMIN only - `PLATFORM_COMMUNITY_MANAGE`, `PLATFORM_PLAN_MANAGE`, `PLATFORM_SUBSCRIPTION_MANAGE`, `PLATFORM_AUDIT_VIEW` (alongside existing `PLATFORM_MANAGE` / `PLATFORM_ANALYTICS`). The auto-generated `rbac.matrix.test.ts` covers the new caps automatically.
- API under `/platform`: `GET /overview` (community/user/flat/subscription counts, active-plan count, MRR from active subscriptions, 6-month new-community growth, recent communities), `GET/POST /communities`, `GET /communities/:id`, `PATCH /communities/:id/status`, `PUT /communities/:id/subscription`, `GET/POST /plans`, `PATCH /plans/:id`, `GET /subscriptions`, `GET /audit`. Community creation slugifies the name (uniquified), then creates the community + `CommunitySetting` + a 30-day `TRIAL` subscription (chosen plan, else the cheapest active plan). Plans store features as a JSON string array; `normalizeFeatures` also reads the legacy object-shaped feature map used by the seed.
- Web `/platform`: Overview (stat tiles + growth bars + recent communities), Communities (create/search/suspend-reactivate/assign plan), Plans (create/enable-disable), Subscriptions (status-filtered list) and Audit (searchable log). The `DashboardHome` placeholder index is replaced and nav gains a Subscriptions entry. Nothing deferred this phase.
## Phase 13
- New model `DemoLead` (name, email, phone, communityName, flats?, message?, status, ip, timestamps) + enum `DemoLeadStatus` (NEW|CONTACTED|CONVERTED|DISMISSED). It is platform-level data with no `communityId`, so it is deliberately NOT registered in `TENANT_MODELS`. Migration `20261010073759_phase13_marketing`.
- Public marketing API: `POST /api/v1/leads` (no auth) with the stricter `authLimiter` (anti-spam), validated by the shared `leadCreateSchema`. Platform management adds `PLATFORM_LEAD_MANAGE` (SUPER_ADMIN only) for `GET /platform/leads` (search + status filter + pagination) and `PATCH /platform/leads/:id`; both write `LEAD.CREATE` / `PLATFORM.LEAD.STATUS` audit rows.
- Web landing page (`LandingPage`) is served at `/` for anonymous visitors; an authenticated user hitting `/` is redirected to their role home (`LandingGate`). ## Phase 14 — Hardening + deployment
- Hardened the error envelope in `errors/handler.ts`: body-parser failures now map to `400 INVALID_JSON` and `413 PAYLOAD_TOO_LARGE`, any carried 4xx HTTP status is passed through as `BAD_REQUEST`, and genuinely unexpected errors still return the generic `500 INTERNAL` (no stack/serialization leakage).
- Health probes: `/health` (liveness alias), `/health/live` and `/health/ready` (runs `SELECT 1` against Postgres, returns `503 NOT_READY` if the DB is unreachable). All health routes are mounted BEFORE the global rate limiter so orchestrators are never throttled.
- Graceful shutdown in `server.ts`: `SIGTERM`/`SIGINT` stop accepting connections, close Socket.IO (`closeSocket`) and `prisma.$disconnect()`, with a 10s forced-exit watchdog. `unhandledRejection`/`uncaughtException` are logged (the latter triggers shutdown). Explicit `keepAliveTimeout`/`headersTimeout`/`requestTimeout`.
- Deployment artifacts (config-only, not run in this environment): `apps/api/Dockerfile` (multi-stage; builds shared → prisma generate → API, runs `migrate deploy` on boot), `apps/web/Dockerfile` (Vite build → nginx), `apps/web/nginx.conf` (SPA fallback, immutable asset caching, `/api` + `/socket.io` proxy, security headers, gzip), `docker-compose.prod.yml` (postgres + redis + api + web with healthchecks), root `.dockerignore`, and GitHub Actions `.github/workflows/ci.yml` (postgres service → `npm ci` → typecheck → lint → api tests → build).
- `docker-compose.prod.yml` is an isolated Compose project (`name: superlink-prod`) with its own `prod_pgdata`/`prod_redisdata` volumes and no fixed `container_name`, so it can run alongside the dev stack without clobbering it (web also uses `depends_on: service_healthy`). Verified end-to-end: `up -d --build` brought all four services up healthy and traffic was exercised through the nginx reverse proxy (SPA served, `/health` proxied to the API, unauth `401`, and a public `POST /leads` persisted to Postgres).
- StorageAdapter / EmailProvider / Push / WhatsApp adapters remain mock/in-memory at v1; file-upload models (complaint attachments, visitor photos, receipts) are still intentionally deferred. Both images are built on `node:22-slim` (Debian/glibc) so the pinned `argon2` prebuilt binary loads correctly; `npm ci --ignore-scripts` skips the workspace `postinstall` (which would run before sources are copied), and `prisma generate` runs explicitly in the builder.
